---
title: "Where do coding agents struggle?"
date: "November 1, 2026"
dateISO: "2026-11-01"
---

From my experience using coding agents thus far, I wanted to share a few examples of where they haven't solved a problem particularly well. As a caveat, I've spent my career so far working on enterprise software products that leverage pretty common CRUD and frontend patterns, so some of the issues described below are more likely related to poor context than model capabilities.

### 1. Agents are not great product designers

This probably has to do with my own weakness in product design and working at earlier-stage companies with less built-out design systems, but I've found coding agents to be pretty bad at product design. This applies to both visual choices (choosing the right colors, fonts, etc.) and product design itself (understanding visual hierarchy, picking which components to use, where they go on a page, etc.). Often, my longest back-and-forths with a coding agent come down to requesting a frontend change, getting back a UI that looks functional but not professional, and then slowly iterating toward a final state. I think this comes down to agents struggling to reason about product design, which is rooted in understanding the customer. Design also has a less verifiable loop compared to coding. This makes me think that 1) product designers will still have a very important role, especially beyond visual design, and 2) there is actually more value than ever before for product-minded engineers to learn the fundamentals of product design, since they have the tools to build things end-to-end. On the visual side, I've found that building a design system in a tool like Figma or Paper can help give agents the ability to create realistic designs, but at least for now, they are not at a place where they can take general product requirements and turn them into a clean design in one pass.

### 2. Agents struggle when primitives are not consistent in the codebase

I've found that if you have clean and consistent patterns in a codebase, a coding agent does a great job of leveraging those patterns for an additional feature. For example, if you are building a new API endpoint and there is a consistent usage pattern of FastAPI or Django REST Framework, the coding agent will consistently put up a PR with good code quality that is easy for a human engineer to reason about and review. The converse is also true. One of the main friction points I've had when trying to use coding agents and get fast code review is when there are multiple ways of accomplishing similar functionality sprinkled across the codebase. If the agent has to decide whether to leverage a `useEffect` because someone once introduced it to quickly ship a feature, it will, in many cases, make the wrong choice, or at least a choice that the code reviewer may disagree with or need more time to reason about. In my opinion, this is the greatest leverage that teams that have historically had low technical debt have: in a world where all engineering teams are moving to agent-driven development, those that have built consistent primitives from day one will have an easier time shipping higher-quality code faster with coding agents. This will be especially pertinent when building new products. There is probably value in being even more critical and intentional about system design at the start, as making the right decisions will have compounding advantages later in the development lifecycle.

### 3. Agents cannot replace product thinking

Coding agents default to building software. This is helpful when the clear solution to a customer or system problem is to write new software or modify an existing piece of software.

However, building software is sometimes not the solution. There are instances when the best way to solve a problem for the customer is to ask them to simplify their own workflow, use your product in a different way, or think about the problem differently. For example, I've been in situations where one or two customers will ask for tangentially related features, and I will pass off the context to the coding agent. The agent will produce code that builds the feature, and it will work great. However, when thinking about the problem through a more rigorous lens, it became clear that the feature was unnecessary or the wrong choice. The coding agent's default action is to produce code that satisfies the request. As I discussed in my piece on [technical judgment](/posts/what-does-good-technical-judgment-actually-look-like), the value of coding agents will accrue most to the engineers who can reason about their customers' problems from first principles. With software factories these days, I think the main bottleneck shifts to building the right context and guardrails that ensure coding agents know when and when not to write software.
